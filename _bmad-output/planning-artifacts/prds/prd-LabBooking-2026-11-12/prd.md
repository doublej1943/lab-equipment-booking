# LabBooking PRD

> Vision + Features 草稿。本文继承 Product Brief v0.1 的 In Scope/Out of Scope，不修改 Product Brief。Product Brief 文件当前仍为 `status: draft`，虽项目说明称其已完成组长内容审核；该状态差异保留待团队确认。

## 0. 文档目的

本 PRD 面向产品负责人、团队成员、测试负责人以及后续 Epic/Story 拆分人员。它将产品愿景、用户旅程、业务术语、按模块分组的稳定 FR、可测量 NFR、MVP 范围和开放问题连接起来。当前为 Discovery 草稿，不是最终批准文档；不包含架构设计、ADR 正文、正式 Story 或业务代码。

## 1. Vision

LabBooking 是面向实验室学生、研究人员和实验室管理员的 Web 设备预约系统。它集中呈现设备状态和半天可预约时段，让普通用户能够在一次清晰流程中查询、预约和管理自己的预约，让管理员能够维护设备并查看全部预约。

产品首要价值是保护预约一致性：同一设备、同一日期、同一半天时段最多存在一条有效 `Confirmed` 预约。系统自动拒绝冲突，不要求管理员逐条审批，从而在四人、四周、两个 Sprint 的限制内交付可运行、可验证、可演示的 MVP。

产品不通过隐式取消或复杂状态流转处理异常。设备停用保留已有预约，预约记录保留 `Confirmed`/`Cancelled` 状态；“已结束”仅依据业务时间计算展示。通知、统计、复杂权限和跨实验室调度不属于本 MVP。

## 2. Target User

### 2.1 Jobs To Be Done

- 学生/研究人员：在开始实验前确认设备和时段是否可用，成功预约而不与他人重复占用。
- 学生/研究人员：查看自己的预约历史，及时取消尚未开始的本人预约，使时段重新开放。
- 实验室管理员：维护设备可用性，停用不应继续接受新预约的设备，并识别其关联的未来预约。
- 实验室管理员：查看全部预约以支持线下协调，但不代替普通用户取消预约。

### 2.2 Non-Users（MVP）

- 不面向需要分钟级预约、在线支付、通知订阅、No-Show 处罚或跨实验室调度的用户。
- 不提供复杂角色体系或学校统一身份认证。

### 2.3 Key User Journeys

- **UJ-1. 学生身份的普通用户在实验前预约空闲设备。** 普通用户（学生身份场景）登录后查询设备，选择日期和上午/下午时段，提交合法且未冲突的预约，看到 `Confirmed` 记录。
- **UJ-2. 研究人员身份的普通用户取消本人尚未开始的预约。** 普通用户（研究人员身份场景）打开个人预约，选择本人且状态为 `Confirmed`、时段尚未开始的记录，取消后看到 `Cancelled`，该时段重新可预约。
- **UJ-3. 用户面对冲突或重复提交。** 用户提交已被有效预约的设备时段，系统拒绝创建第二条有效记录，提示设备标识、日期和时段，不披露其他预约人的姓名或联系方式。
- **UJ-4. 管理员停用设备并识别影响。** 管理员停用设备后，该设备继续可见但不能接受新预约；已有预约保持原状态，管理员可查看其未来预约以线下协调。

## 3. Glossary

- **普通用户**：学生或研究人员，只能管理自己的预约。
- **管理员**：实验室管理角色，可维护设备并查看全部预约，不可代替普通用户取消预约。
- **设备**：可被预约的实验室资产；MVP 不支持物理删除。
- **可用（Available）**：设备可以接受符合规则的新预约。
- **已停用（Disabled）**：设备不能接受新预约，但已有预约不自动取消。
- **预约**：普通用户针对一个设备、一个日期和一个半天时段创建的记录。
- **有效预约**：持久化状态为 `Confirmed` 的预约。
- **已确认（Confirmed）**：预约已成功创建并占用对应时段。
- **已取消（Cancelled）**：预约已被符合条件的操作取消，不再占用时段。
- **业务时区**：用于判断时段开始/结束、当天预约和取消资格的统一时区；当前 `Asia/Shanghai` 仅为课程演示环境 `[ASSUMPTION]`。

## 4. Features

### 4.1 Auth：用户身份与权限

**Description：** 系统识别普通用户和管理员，并在服务端执行身份、角色和预约所有权校验。前端隐藏按钮不是安全边界。

#### FR-AUTH-01：用户身份识别

普通用户或管理员可以使用预设测试账号登录并进入其授权功能。

**前置条件与规则：** 账号属于系统已知角色；未认证请求不得访问需要登录的个人或管理数据。

**预期结果：** 系统建立可用于后续请求的身份上下文；登录失败不泄露账号是否存在的额外信息。

**异常：** 无效凭据被拒绝；未认证访问受保护资源被拒绝。

**验收（Given-When-Then）：** Given 一个预设普通用户账号，When 提供有效凭据登录，Then 系统识别其为普通用户并允许访问设备查询和个人预约功能；Given 无效凭据，When 尝试登录，Then 不创建已认证会话。

#### FR-AUTH-02：服务端角色与所有权校验

服务端必须对每个受保护操作校验身份、角色和资源所有权，不得仅依赖前端按钮隐藏。

**前置条件与规则：** 预约取消必须同时满足操作人为预约本人、状态为 `Confirmed`、时段尚未开始。

**预期结果：** 越权操作被拒绝，目标数据不变，不向操作者披露其他用户不应看到的信息；具体 HTTP 状态码留待 Architecture/API 阶段。

**异常：** 用户 A 修改 URL、预约 ID 或请求体尝试取消用户 B 的预约时，操作被拒绝。

**验收（Given-When-Then）：** Given 用户 B 有一条尚未开始的 `Confirmed` 预约，When 用户 A 直接请求取消该预约，Then 服务端拒绝操作、预约状态保持不变且不返回用户 B 的个人信息。

### 4.2 Device：设备查询与维护

**Description：** 普通用户查询设备及状态；管理员新增、编辑、启用和停用设备。设备停用不等于删除，也不自动取消已有预约。

#### FR-DEV-01：设备查询与状态展示

普通用户和管理员可以查询设备及其 `Available`/`Disabled` 状态。

**前置条件与规则：** 查询要求用户已认证；已停用设备继续显示并明确标记。未认证请求不得查询设备列表。

**预期结果：** 用户可以据此选择设备和日期时段；不要求展示其他预约人的身份信息。

**异常：** 无设备或查询条件无结果时返回可识别的空结果，不伪造可用状态。

**验收（Given-When-Then）：** Given 已认证用户且系统有可用和已停用设备，When 用户查询设备列表，Then 两类设备均显示且状态明确；Given 未认证用户，When 查询设备列表，Then 请求被拒绝并获得需要登录的明确反馈。

#### FR-DEV-02：设备新增与可编辑信息

管理员可以新增设备，并编辑已创建设备的名称、位置等业务信息。设备至少包含唯一设备标识、名称、位置和启停状态；设备唯一标识在创建后不可修改；其他字段（例如描述、型号或使用说明）待团队确认。设备启停操作及其业务后果统一遵循 FR-DEV-03。

**前置条件与规则：** 只有管理员可操作；新增设备时设备标识必须唯一，创建后不可修改；MVP 不支持物理删除或批量导入。字段集合以最低要求为准，未确认的扩展字段不得作为 MVP 必需条件。启停状态的修改和业务后果以 FR-DEV-03 为准。

**预期结果：** 合法业务信息变更可在后续查询中识别；普通用户的直接请求被服务端拒绝。

**验收（Given-When-Then）：** Given 管理员已认证，When 提交包含唯一设备标识、名称、位置和启停状态的合法新设备信息，Then 设备出现在查询结果中；Given 已存在相同设备标识，When 管理员再次提交新增请求，Then 新设备不被创建且原设备不被覆盖；Given 管理员已认证且已有设备，When 提交仅修改名称、位置等原需求允许的业务信息，Then 同一设备标识对应的设备被更新且不创建新设备；Given 管理员尝试修改已有设备的唯一标识，When 提交编辑请求，Then 请求被拒绝且原设备标识和其他信息不变；Given 普通用户，When 直接请求新增或编辑设备，Then 设备不被创建且既有设备不被修改。

#### FR-DEV-03：启用与停用设备

管理员可以启用或停用设备；已停用设备不能接受新预约。

**前置条件与规则：** 只有管理员可操作启停；启用使设备恢复为可接受新预约的状态，停用使设备不能接受新预约；停用不自动取消已有预约，已有预约状态与历史记录保持不变。

**预期结果：** 停用设备继续可见并显示统一的“设备已停用”状态提示；不要求保存或展示专门的停用原因字段；管理员可识别其未来预约。

**验收（Given-When-Then）：** Given 设备有未来 `Confirmed` 预约，When 管理员停用设备，Then 原预约保持原状态，设备显示 `Disabled` 及统一的“设备已停用”提示，新的预约请求被拒绝且明确说明设备已停用；Given 设备处于 `Disabled`，When 管理员启用设备，Then 设备显示 `Available` 并可继续接受符合 FR-BOOK-01、02、03 的新预约，既有预约记录不被改变。

### 4.3 Booking：预约创建、冲突、记录与取消

**Description：** 预约使用半天粒度，不支持任意分钟。暂定上午 08:00–12:00、下午 13:30–17:30，时间边界为 `[ASSUMPTION]`，待实际使用者确认。允许预约当天尚未开始的时段；禁止过去日期、已经开始或已经结束的时段。业务时区必须统一；`Asia/Shanghai` 仅为演示环境 `[ASSUMPTION]`。

#### FR-BOOK-01：半天时段选择与时间资格

普通用户可以为设备选择日期和上午/下午半天时段。

**前置条件与规则：** 不支持分钟级区间；当天仅允许尚未开始的时段；过去日期和已开始/已结束时段不得创建预约。

**预期结果：** 合法时间选择进入预约提交；非法选择被拒绝并说明日期或时段不可用。

**验收（Given-When-Then）：** Given 业务时间为当天 07:30，When 用户选择当天上午时段，Then 请求可继续；Given 业务时间为当天 08:00，When 用户选择当天上午时段，Then 请求被拒绝；Given 业务时间为当天 12:00，When 用户选择当天下午时段，Then 请求可继续。以上具体边界依赖时段和时区确认。

#### FR-BOOK-02：创建合法预约

普通用户可以为 `Available` 设备创建未冲突的半天预约。

**前置条件与规则：** 用户已认证；日期和时段符合 FR-BOOK-01；目标设备未停用；该设备/日期/时段不存在有效 `Confirmed` 预约。不同设备之间不因同一用户、同一日期和同一半天时段而互相阻塞。

**预期结果：** 创建一条 `Confirmed` 预约，用户可在个人记录中查看。

**异常：** 设备停用、时段非法或请求无身份时创建失败，不能产生部分记录。

**验收（Given-When-Then）：** Given 用户已认证、设备可用且目标时段空闲，When 提交预约，Then 恰好创建一条 `Confirmed` 记录并显示设备、日期和时段。

#### FR-BOOK-03：冲突处理与重复提交

系统必须拒绝同一设备、同一日期、同一半天时段的第二条有效预约，包括来自同一用户的重复提交。

**前置条件与规则：** 只有 `Confirmed` 占用时段；`Cancelled` 不再占用时段。不得泄露其他预约人的姓名或联系方式。

**预期结果：** 冲突请求不创建新有效记录，提示包含设备标识、日期和时段；取消后可重新预约但仍受一致性约束。

**异常：** 并发请求下不得出现双重有效预约；不同设备或不同半天时段不应被错误阻塞。

**验收（Given-When-Then）：** Given 目标时段已有一条 `Confirmed` 预约，When 另一请求提交相同设备、日期和时段，Then 请求被拒绝、有效预约数量保持为一条且提示不含其他用户身份信息；Given 同一普通用户已在某日期某半天成功预约设备 A，且设备 B 在同一日期同一半天空闲，When 该用户提交设备 B 的预约，Then 设备 B 的预约可正常创建为 `Confirmed`，不因设备 A 的预约被错误拒绝。

#### FR-BOOK-04：个人预约记录

普通用户可以查看自己的预约记录，包括 `Confirmed` 和 `Cancelled` 状态；不得查看他人的个人预约数据。预约持久化状态的定义和变更规则以 FR-BOOK-06 为准，本条只规定个人记录的可见范围和展示。

**前置条件与规则：** 仅返回当前用户自己的预约；如界面显示“已结束”，由业务时间计算，不新增状态。

**预期结果：** 用户能区分当前有效、已取消和按时间计算已结束的记录。

**验收（Given-When-Then）：** Given 用户有 `Confirmed`、`Cancelled` 和已结束预约，When 查看个人记录，Then 三类记录均保留，持久化状态只有 `Confirmed`/`Cancelled`，已结束仅为计算展示。

**验收（Given-When-Then）：** Given 用户存在一条尚未开始的 `Confirmed` 预约，管理员将该预约对应设备停用，When 用户查看个人预约记录，Then 该预约仍保持 `Confirmed`，界面明确提示设备已停用，且不自动取消。

#### FR-BOOK-05：本人预约取消

普通用户可以取消自己的、状态为 `Confirmed` 且尚未开始的预约；取消后的状态变更遵循 FR-BOOK-06。

**前置条件与规则：** 操作人必须是预约本人；只有 FR-BOOK-06 定义的 `Confirmed` 预约且时段尚未开始时可取消，已开始、已结束或已为 `Cancelled` 时不可取消。

**预期结果：** 预约状态变为 `Cancelled`，历史记录保留，对应时段重新开放。

**异常：** 越权、重复取消、已开始或已结束取消请求均被拒绝，原状态不被错误改变。

**验收（Given-When-Then）：** Given 用户本人有一条尚未开始的 `Confirmed` 预约，When 请求取消，Then 状态变为 `Cancelled` 且同一时段可被新的合法预约竞争；Given 预约已开始，When 请求取消，Then 状态不变。

#### FR-BOOK-06：预约状态边界

FR-BOOK-06 是预约持久化状态和状态变更的统一规则来源；MVP 持久化预约状态仅包括 `Confirmed` 和 `Cancelled`。FR-BOOK-02 负责创建 `Confirmed`，FR-BOOK-05 负责符合条件的本人取消并变更为 `Cancelled`，FR-BOOK-04 只负责记录查看与计算展示。

**前置条件与规则：** 不自动转换为 `Completed`；不因设备停用自动取消或改约。

**预期结果：** 只有符合条件的创建或本人取消操作可以产生状态变更；设备停用、时间经过或记录查看均不改变持久化状态，已结束仅为计算展示。

**验收（Given-When-Then）：** Given 一个已结束但未取消的 `Confirmed` 预约，When 系统刷新或经过时间边界，Then持久化状态仍为 `Confirmed`，界面可计算显示已结束。

#### FR-BOOK-07：设备半天时段可用性查询

普通用户和管理员在完成认证后，可以在选择设备与日期后，分别查询上午和下午半天时段当前是否可预约，以及是否存在有效预约占用。

**前置条件与规则：** 查询结果只反映查询时刻的状态；只统计 `Confirmed` 预约，`Cancelled` 不占用时段；已停用设备仍可查询并显示停用状态，但不得作为可预约设备；对合法日期分别判断上午和下午时段，已开始或已结束的时段标记为不可预约，不因其中一个时段不可预约而使整天查询失败；不得展示其他预约人的姓名、联系方式或其他个人信息。查询要求用户已认证。

**预期结果：** 页面分别展示上午、下午时段的可预约、已占用或不可预约状态；已占用但时间合法的时段显示占用状态，已开始或已结束的时段明确标记为不可预约；查询结果不替代 FR-BOOK-01、02、03，真正创建预约时仍须重新校验时间资格、设备状态和冲突。

**异常：** 已停用设备的查询仍返回设备及停用状态提示，但针对该设备的新预约必须被拒绝；非法日期被拒绝并明确提示；合法日期下已过期、已开始或已结束的时段返回不可预约标记，不使同日另一时段的查询失败；合法但已被占用的时段返回占用状态；未认证用户不得查询并获得需要登录的明确反馈；并发变化不得导致页面查询结果被当作预约保证。

**验收（Given-When-Then）：** Given 已认证用户选择一个可用设备和合法日期，且上午已有 `Confirmed` 预约、下午没有有效预约，When 查询半天时段可用性，Then 页面显示上午已占用、下午可用，且不显示预约人的个人信息；Given 合法日期下上午时段已经开始或结束、下午时段尚未开始，When 用户查询半天时段可用性，Then 查询成功，上午明确显示不可预约、下午独立显示可预约或已占用；Given 已认证用户选择已停用设备，When 查询半天时段可用性，Then 设备仍可查询并显示 `Disabled`/“设备已停用”提示，且不能将该设备时段作为可预约选项；Given 已认证用户提交非法日期，When 系统处理请求，Then 请求被拒绝并给出明确的日期提示；Given 用户尝试创建已开始或已结束时段的预约，When 提交创建请求，Then FR-BOOK-01、02、03 的校验拒绝创建；Given 未认证用户，When 查询设备半天时段可用性，Then 请求被拒绝并获得需要登录的明确反馈；Given 查询时下午显示可用，When 另一请求在创建前成功占用下午，Then 用户提交预约时仍执行冲突检查并拒绝第二条有效预约。

### 4.4 Admin：管理员查询与设备管理

**Description：** 管理员可以查看全部预约、筛选停用设备关联的未来预约，并维护设备；不提供代用户取消、逐条审批、自动通知或自动改约。

#### FR-ADM-01：查看全部预约

管理员可以查看系统内全部预约及其设备、日期、时段和预约状态。

**前置条件与规则：** 只有管理员可访问；展示遵循最小必要信息原则，可查看预约人标识以支持线下协调，但不默认展示联系方式。

**预期结果：** 管理员能识别预约记录、状态和预约人标识，支持线下协调；联系方式不默认展示。

**验收（Given-When-Then）：** Given 系统存在多个用户的预约且记录包含预约人标识和联系方式，When 管理员查看全部预约，Then 可看到设备、日期、时段、状态和必要的预约人标识，但默认不展示联系方式；Given 普通用户，When 直接请求管理员专用的全部预约查询，Then 服务端拒绝请求且不返回其他用户的预约或个人信息。

#### FR-ADM-02：识别停用设备未来预约

管理员可以识别已停用设备关联的未来预约。

**前置条件与规则：** 只有管理员可访问；未来由业务时区和预约时段计算；仅将已停用设备关联且时段尚未开始的 `Confirmed` 预约列为需要线下协调的预约；已取消预约不列为仍需协调；结果可包含预约人标识但不默认包含联系方式；不新增“待确认”状态。

**预期结果：** 结果仅包含已停用设备的未来 `Confirmed` 预约，可用于线下协调；管理员可识别预约人标识，原预约状态不被自动改变；已取消预约不被错误标记为仍需协调，联系方式不默认展示。

**验收（Given-When-Then）：** Given 已停用设备存在未来 `Confirmed`、未来 `Cancelled` 和过去 `Confirmed` 预约，When 管理员筛选需要线下协调的受影响预约，Then 仅返回未来 `Confirmed` 预约及其预约人标识，不返回未来 `Cancelled` 或过去预约，不默认展示联系方式，且所有原预约状态保持不变；Given 普通用户，When 直接请求管理员专用的停用设备未来预约查询，Then 服务端拒绝请求且不返回其他用户信息。

#### FR-ADM-04：管理员取消边界

MVP 不支持管理员代替普通用户取消预约。

**权限关系：** FR-AUTH-02 是所有受保护操作的通用身份、角色和资源所有权校验；本条是管理员代取消的专项业务禁止规则。管理员身份不会产生代替普通用户取消预约的权限，两项约束同时适用。

**验收（Given-When-Then）：** Given 管理员查看一条用户预约，When 管理员尝试取消该预约，Then 服务端拒绝操作，预约状态保持不变；管理员只能通过 FR-ADM-02 识别并线下协调。

## 5. Cross-Cutting NFRs

### NFR-01：并发预约一致性

同一设备、同一日期、同一半天时段最多存在一条有效 `Confirmed` 预约。

`[ASSUMPTION]` 测试负责人确认前，暂定使用 20 个独立有效请求同时预约同一空闲时段，预期恰好一个成功、其余因冲突拒绝；重置状态后重复 50 轮，双重有效预约次数必须为 0。同时验证不同设备、不同半天时段可分别成功。测试必须使用独立请求和实际数据库连接。数据库锁、事务或其他实现方式不在本 PRD 中指定。

通过标准：所有轮次双重有效预约次数为 0，且无错误阻塞不同设备/不同时段的合法请求。当前没有实际测试结果。

### NFR-02：设备列表响应时间

`[ASSUMPTION]` 测试负责人确认前，暂定在 100 台设备、1000 条历史预约、20 个并发读取用户条件下，累计至少执行 1000 个设备列表查询请求，P95 响应时间 ≤ 1000ms，且无未预期服务端错误。

测试记录必须包含机器配置、测试工具和版本、并发模型、测试数据规模与生成方式、请求计时范围、响应时间统计方法、异常请求处理和通过标准。未执行的测试不得写成已验证结果。预约写入接口性能目标暂不纳入已确认需求，作为后续讨论项。

### NFR-03：服务端授权保护

所有需要身份、角色或预约所有权的操作必须在服务端验证；直接构造请求不得绕过权限边界。测试覆盖范围至少包括：未认证访问设备列表、个人预约、设备维护、管理员全部预约和半天时段查询；普通用户访问设备新增/编辑/启停、全部预约和管理员操作；用户 A 取消用户 B 的预约；管理员代替用户取消预约；以及篡改 URL、预约 ID 或请求体后的直接请求。

**通过标准：** 每个合法访问场景成功完成相应操作；每个未授权或越权场景均被拒绝，未授权数据修改次数为 0，目标预约和设备数据保持不变，且不泄露受保护的用户姓名、联系方式或其他个人信息。具体权限框架和 HTTP 状态码留待 Architecture/API 阶段。

## 6. Non-Goals（MVP）

- 管理员逐条审批、多级审批或管理员代替用户取消。
- 邮件、短信、微信通知。
- No-Show、处罚、违约限制。
- 设备物理删除、自动取消或自动改约。
- 统计报表、可视化大屏、独立手机 App、微信小程序。
- 任意分钟级预约、在线支付、设备维修工单、复杂维护流程、批量导入。
- 学校统一身份认证、复杂权限系统、多实验室跨区域调度。
- AI 智能排班、设备推荐。

## 7. MVP Scope

### 7.1 In Scope

- 预设测试账号登录；普通用户和管理员角色。
- 服务端身份、角色和预约所有权校验。
- 设备查询、新增、编辑、启用、停用；不支持物理删除。
- 日期与半天预约；合法创建、冲突拒绝、个人记录和符合条件的本人取消。
- `Confirmed`/`Cancelled` 预约状态及记录保留。
- 停用设备禁止新预约，已有预约不自动取消；管理员识别未来受影响预约。

### 7.2 Out of Scope for MVP

严格继承 Product Brief Out of Scope，见本节 Non-Goals。不得在本 PRD 阶段新增未获组长批准的功能；若后续提出新增功能，需说明理由、成本和四周交付影响并更新决策日志。
